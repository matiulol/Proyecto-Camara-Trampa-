## 1. Objetivo de la etapa

El objetivo de esta etapa es separar dos conceptos del sistema:

- Peticiones: solicitudes que el usuario realiza desde el dashboard para pedir que una cámara haga algo.
- Eventos: información visual de actividad ya registrada por cámaras.

La arquitectura implementada es:

```text
Dashboard -> FastAPI -> MongoDB
                    ^
                    | HTTP polling y resultado
                Raspberry -> Picamera2
```

La carpeta `raspberry_prueba/` forma parte del proyecto. Su interfaz funciona como
monitor de peticiones y no como una pantalla de captura manual.

## 3. Colección peticiones

La colección `peticiones` guarda solicitudes realizadas desde el dashboard.

Estructura implementada:

```json
{
  "_id": "ObjectId generado por MongoDB",
  "camara_id": "camara001",
  "tipo": "foto",
  "estado": "pendiente",
  "fecha_hora": "2026-09-20 18:30:00"
}
```

Campos:

- `_id`: ObjectId generado por MongoDB.
- `camara_id`: ID textual de una cámara existente, por ejemplo `camara001`.
- `tipo`: acción solicitada.
- `estado`: estado actual de la petición.
- `fecha_hora`: fecha y hora en que FastAPI creó la petición.

Tipos permitidos:

- `foto`
- `video`

Estados permitidos:

- `pendiente`: la solicitud fue creada y todavía no fue ejecutada por la Raspberry.
- `ejecutado`: la Raspberry realizó correctamente la solicitud.
- `error`: la solicitud no pudo ejecutarse correctamente.

Las peticiones no crean eventos automáticamente.

## 4. Relación con cámaras

Cada petición debe estar asociada a una cámara existente.

Relación:

```text
camaras._id -> peticiones.camara_id
```

Ejemplo:

```text
camaras._id = camara001
peticiones.camara_id = camara001
```

Antes de crear una petición, el backend verifica que exista una cámara con ese `_id`.

## 6. Endpoints de peticiones

`POST /api/v1/peticiones`

Crea una petición para una cámara existente.

Ejemplo de cuerpo:

```json
{
  "camara_id": "camara001",
  "tipo": "foto"
}
```

Respuesta: devuelve la petición creada con estado inicial `pendiente`.

`GET /api/v1/peticiones`

Lista el historial de peticiones.

`GET /api/v1/peticiones/{peticion_id}`

Consulta una petición específica por su ObjectId.

`PUT /api/v1/peticiones/{peticion_id}`

Actualiza únicamente el estado de la petición.

Ejemplo:

```json
{
  "estado": "ejecutado"
}
```

Solo se aceptan `pendiente`, `ejecutado` y `error`.

`GET /api/v1/peticiones/pendientes/{camara_id}`

Es consultado periódicamente por la Raspberry asociada a esa cámara. Devuelve la
petición pendiente más antigua o `null` si no existe ninguna.

`PUT /api/v1/peticiones/{peticion_id}/resultado`

Es llamado por la Raspberry después de una captura. Un resultado ejecutado debe
incluir `nombre_archivo` y `ruta_local`; FastAPI inserta el metadato en `archivos`
y guarda `archivo_id` en la petición. Un resultado con error guarda `mensaje_error`.

## 8. Dashboard PySide6

El dashboard mantiene el login existente y la pantalla principal con el usuario autenticado.

Pestañas:

- Cámaras
- Peticiones
- Eventos

### Cámaras

Mantiene la administración existente:

- Agregar cámara.
- Consultar cámara.
- Editar cámara.
- Eliminar cámara.
- Actualizar.

### Peticiones

Permite:

- Seleccionar una cámara existente.
- Solicitar foto.
- Solicitar video.
- Consultar una petición seleccionada.
- Actualizar el historial.
- Ver ID, cámara, tipo, estado y fecha/hora.

Cuando el usuario solicita una foto o un video:

1. El dashboard toma el `camara_id` seleccionado.
2. El dashboard envía `POST /api/v1/peticiones`.
3. FastAPI valida que la cámara exista.
4. FastAPI crea el documento en `Ani_cam.peticiones`.
5. MongoDB genera el `_id`.
6. La petición queda con estado `pendiente`.
7. El dashboard refresca el historial.

### Eventos

Permite:

- Consultar un evento seleccionado.
- Actualizar la tabla.

Si no existen eventos, se muestra la tabla vacía con un mensaje apropiado.

Eventos representa actividad registrada. Peticiones representa solicitudes realizadas.

## 10. Archivos principales

Backend:

- `backend/main.py`: registra los routers principales y comprueba MongoDB al iniciar.
- `backend/config/settings.py`: mantiene la configuración de `Ani_cam`.
- `backend/models/schemas.py`: define modelos Pydantic de autenticación, cámaras, peticiones y eventos.
- `backend/routers/peticiones.py`: implementa creación, listado, consulta y actualización de peticiones.
- `backend/routers/eventos.py`: expone eventos como consulta de solo lectura.
- `backend/database/object_id.py`: serializa ObjectId y datetime para respuestas JSON.

Dashboard:

- `desktop_app/services/api_client.py`: comunica PySide6 con FastAPI.
- `desktop_app/widgets/main_window.py`: contiene login, dashboard, pestañas y acciones de usuario.

## 11. Raspberry Pi

La Raspberry consulta FastAPI por HTTP con su `camara_id`. Cuando recibe una
petición de foto, reutiliza `ControladorCamara.tomar_foto`; para video reutiliza
la grabación MP4 existente durante una duración configurable. Al terminar, informa
el resultado a FastAPI. Si el backend no responde, la ventana sigue abierta e indica
la desconexión. La prueba física de cámara requiere la Raspberry y no se ejecuta en
la computadora de desarrollo.

## 12. Cómo probar

Iniciar MongoDB con la base `Ani_cam`.

Iniciar backend:

```bash
cd backend
.venv\Scripts\activate
uvicorn main:app --reload
```

Probar endpoints:

1. `GET /api/v1/camaras`
2. `POST /api/v1/peticiones` con `tipo` = `foto`
3. `POST /api/v1/peticiones` con `tipo` = `video`
4. `GET /api/v1/peticiones`
5. Verificar que las peticiones nacen como `pendiente`
6. `PUT /api/v1/peticiones/{id}` con `estado` = `ejecutado`
7. `PUT /api/v1/peticiones/{id}` con `estado` = `error`
8. Intentar un estado inválido y verificar rechazo
9. Intentar crear una petición con cámara inexistente y verificar error
10. `GET /api/v1/eventos`
11. Verificar que no exista creación de eventos desde el dashboard
12. Verificar que la pestaña Eventos solo consulte y muestre información

Iniciar dashboard:

```bash
cd desktop_app
.venv\Scripts\activate
python main.py
```
