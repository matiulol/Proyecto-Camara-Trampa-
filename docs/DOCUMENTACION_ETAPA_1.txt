# DOCUMENTACIÓN DE LA INTEGRACIÓN DASHBOARD FASTAPI RASPBERRY PI

Fecha de actualización: 25-09-2026
Proyecto: Cámara Trampa Inteligente para Reserva Natural
Base de datos: Ani_cam

## 1. Propósito de esta etapa

Esta etapa continúa el sistema existente sin reemplazar su arquitectura. El
objetivo fue conectar la aplicación de Raspberry Pi con FastAPI mediante HTTP
para que una petición creada en el Dashboard pueda ser ejecutada por la cámara.

La solución utiliza polling. La Raspberry consulta periódicamente a FastAPI si
hay una petición pendiente para su cámara. FastAPI es el único componente que
accede a MongoDB; la Raspberry no conoce ni utiliza la URI de la base de datos.

## 2. Arquitectura implementada

```text
Usuario
  |
  v
Dashboard PySide6
  |
  | POST /api/v1/peticiones
  v
FastAPI -------------------- MongoDB Ani_cam
  ^                              |
  | GET petición pendiente        | peticiones y archivos
  | PUT resultado                 v
Raspberry Pi con PySide6 y Picamera2
  |
  v
Foto JPEG o video MP4 en la tarjeta SD
```

El Dashboard no se comunica directamente con la Raspberry. El Dashboard crea y
consulta peticiones a través de FastAPI. La Raspberry también usa FastAPI, pero
solo para pedir su trabajo pendiente e informar su resultado.

## 4. Flujo de una petición de foto

1. El usuario selecciona `Camara 1` en la pestaña Peticiones del Dashboard.
2. El usuario presiona `Solicitar foto`.
3. El Dashboard envía `POST /api/v1/peticiones` a FastAPI con `camara_id` y
   `tipo: foto`.
4. FastAPI verifica que `camara001` existe en `Ani_cam.camaras`.
5. FastAPI crea el documento en `Ani_cam.peticiones` con estado `pendiente`.
6. La Raspberry configurada con `CAMARA_ID=camara001` consulta periódicamente
   el endpoint de pendientes.
7. FastAPI devuelve la petición pendiente más antigua de esa cámara.
8. La Raspberry usa `ControladorCamara.tomar_foto` para generar el JPEG local.
9. La Raspberry llama a FastAPI para informar el resultado y la ruta local.
10. FastAPI inserta los metadatos en `Ani_cam.archivos`, enlaza el archivo con
    la petición y cambia su estado a `ejecutado`.
11. Cuando el Dashboard actualiza la tabla, muestra `ejecutado` y el nombre del
    archivo. La Raspberry permite ver la imagen local en su propia interfaz.

Si la cámara no puede capturar la imagen, la Raspberry informa `error` y un
mensaje explicativo. FastAPI guarda ese mensaje en la petición.

## 5. Flujo de una petición de video

El inicio del flujo es igual al de foto. La diferencia es la ejecución local:

1. La Raspberry recibe una petición cuyo `tipo` es `video`.
2. `ControladorCamara.iniciar_video` inicia la grabación con Picamera2,
   `H264Encoder` y `FfmpegOutput`.
3. Después de la duración configurada, `ControladorCamara.detener_video`
   finaliza el MP4.
4. La Raspberry informa el resultado a FastAPI.
5. FastAPI registra el archivo y actualiza la petición a `ejecutado`.

La duración por defecto es diez segundos. Se puede cambiar sin editar código
definiendo la variable de entorno `DURACION_VIDEO_SEGUNDOS`.

## 6. Colecciones y relaciones de MongoDB

La base utilizada continúa siendo exclusivamente `Ani_cam`.

### camaras

La cámara utiliza un identificador textual, por ejemplo:

```json
{
  "_id": "camara001",
  "nombre": "Camara 1",
  "ubicacion": "Sector Norte",
  "estado": "activa"
}
```

### peticiones

Una petición representa una orden explícita del usuario, no un evento de cámara.

```json
{
  "_id": "ObjectId generado por MongoDB",
  "camara_id": "camara001",
  "tipo": "foto",
  "estado": "pendiente",
  "fecha_hora": "2026-09-25 10:30:00"
}
```

Después de una ejecución correcta se agregan `archivo_id` y `nombre_archivo`.
Después de un fallo se agrega `mensaje_error`. Estos campos son opcionales para
mantener la compatibilidad con las peticiones creadas antes de esta integración.

### archivos

La colección ya existía. Se mantiene su campo histórico `id_camara`. Para una
captura solicitada se conserva esa relación y se agregan los datos mínimos para
conectarla con la petición:

```json
{
  "id_camara": "camara001",
  "peticion_id": "ObjectId de la petición convertido a texto",
  "tipo": "imagen",
  "nombre_archivo": "/ruta/local/de/la/Raspberry/foto_001.jpg",
  "ruta_local": "/ruta/local/de/la/Raspberry/foto_001.jpg",
  "fecha_hora": "2026-09-25 10:30:15"
}
```

Para video, `tipo` es `video`. No se completa `id_evento`, porque una petición
del Dashboard no debe convertirse artificialmente en un evento.

La relación completa queda así:

```text
camara._id -> peticiones.camara_id
peticiones._id -> archivos.peticion_id
peticiones.archivo_id -> archivos._id
```

## 7. Endpoints relacionados con peticiones

### POST /api/v1/peticiones

Lo consume el Dashboard. Crea una petición en estado `pendiente`.

```json
{
  "camara_id": "camara001",
  "tipo": "foto"
}
```

### GET /api/v1/peticiones

Lo consume el Dashboard para mostrar el historial actualizado de peticiones,
incluido el archivo generado o el mensaje de error cuando existen.

### GET /api/v1/peticiones/pendientes/{camara_id}

Lo consume la Raspberry. Devuelve solo la petición pendiente más antigua de la
cámara indicada; si no hay ninguna, responde `null`. Esta ruta no modifica la
base de datos.

Ejemplo:

```text
GET /api/v1/peticiones/pendientes/camara001
```

### PUT /api/v1/peticiones/{peticion_id}/resultado

Lo consume exclusivamente la Raspberry al finalizar una captura. Acepta solo
los estados finales `ejecutado` o `error`; no permite crear estados nuevos.

Ejemplo de captura correcta:

```json
{
  "estado": "ejecutado",
  "nombre_archivo": "foto_001.jpg",
  "ruta_local": "/home/pi/proyecto/archivos/camara001/fotos/foto_001.jpg"
}
```

Ejemplo de error:

```json
{
  "estado": "error",
  "mensaje_error": "No se pudo inicializar la camara."
}
```

Si una petición ya fue resuelta, FastAPI rechaza otro resultado con HTTP 409.
Esto protege el historial contra actualizaciones tardías o duplicadas.

## 8. Interfaz de la Raspberry

La nueva ventana de `raspberry_prueba` tiene el propósito de supervisar las
peticiones del Dashboard. Muestra el estado de conexión con FastAPI, el ID de
la cámara asociada, el historial recibido durante la sesión, su tipo, estado,
fecha y resultado.

No incluye botones para solicitar una captura manual. La orden nace siempre en
el Dashboard. Cuando una petición ejecutada tiene un archivo local disponible,
la interfaz puede mostrar una foto o reproducir un video.

Si FastAPI deja de responder, la aplicación no se cierra: muestra el estado de
desconexión y vuelve a intentarlo en el siguiente intervalo de consulta.

## 9. Configuración de la Raspberry

En Raspberry Pi OS se mantienen las dependencias de cámara instaladas con apt:

```bash
sudo apt update
sudo apt install -y python3-picamera2 ffmpeg python3-pyside6.qtwidgets python3-pyside6.qtmultimedia
```

También se requiere `requests`, declarado en `raspberry_prueba/requirements.txt`.

Antes de iniciar la aplicación se debe indicar la IP de la computadora que
ejecuta FastAPI. No debe utilizarse `127.0.0.1` para una Raspberry remota,
porque esa dirección apunta a la propia Raspberry.

```bash
export URL_BACKEND="http://192.168.1.50:8000/api/v1"
export CAMARA_ID="camara001"
export INTERVALO_CONSULTA_MS="5000"
export DURACION_VIDEO_SEGUNDOS="10"
python3 main.py
```

La IP `192.168.1.50` es solamente un ejemplo y debe reemplazarse por la IP real
de la PC del backend. FastAPI debe iniciarse escuchando una dirección accesible
desde la red local, no solo `127.0.0.1`.

## 11. Límites actuales

- Los archivos permanecen en la tarjeta SD de la Raspberry; no se suben a la
  nube ni se transfieren al Dashboard.
- La reproducción y visualización de archivos se realiza localmente en la
  Raspberry, no desde el Dashboard.
- No se implementaron MQTT, Redis, RabbitMQ, WebSockets, Docker ni servicios de
  mensajería, porque no son necesarios para esta etapa educativa.
- Los eventos continúan siendo un historial independiente y no se crean desde
  las peticiones.

## 12. Archivos principales de la integración

- `backend/models/schemas.py`: validación de resultados y campos opcionales de
  respuesta de peticiones.
- `backend/routers/peticiones.py`: polling, registro de resultado y relación
  con `archivos`.
- `desktop_app/widgets/main_window.py`: columna Resultado en la tabla existente.
- `raspberry_prueba/comunicacion/cliente_backend.py`: cliente HTTP de la Raspberry.
- `raspberry_prueba/interfaz/ventana_principal.py`: monitor de peticiones.
- `raspberry_prueba/config.py`: URL, cámara, intervalo y duración configurables.
- `raspberry_prueba/README.md`: instalación y ejecución en la Raspberry.
