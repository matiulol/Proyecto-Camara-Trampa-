# DOCUMENTACIÓN DE LA INTEGRACIÓN DASHBOARD FASTAPI RASPBERRY PI

Fecha de actualización: 06-10-2026
Proyecto: Cámara Trampa Inteligente para Reserva Natural
Base de datos: Ani_cam

## Configuración de MongoDB local

FastAPI lee la conexión exclusivamente desde `backend/.env`. Copie
`backend/.env.example` a `backend/.env` y mantenga
`MONGODB_URI=mongodb://localhost:27017`, `MONGODB_DATABASE=Ani_cam` y
`MONGODB_TIMEOUT_MS=5000`. ANICAM utiliza MongoDB local; no utiliza MongoDB
Atlas ni crea ni migra otra base de datos.

`backend/.env` está excluido de Git. No coloque URI ni credenciales en código,
documentación, respuestas HTTP o registros. En Windows, compruebe el servicio
con `Get-Service MongoDB` y, si está detenido, inícielo como administrador con
`Start-Service MongoDB`. Al iniciar y en `GET /health`, FastAPI ejecuta un
`ping`; si falla, informa una causa de configuración sin revelar la URI.

## Almacenamiento privado en Backblaze B2

La captura sigue este orden: Picamera2 escribe primero el JPEG o MP4 en la SD,
la Raspberry confirma que existe y tiene contenido, y después lo transmite por
HTTP a FastAPI. El backend, único proceso que conoce las credenciales B2, sube
el flujo mediante `boto3`, registra `clave_b2`, `estado_subida=confirmada` y la
relación con la petición en `Ani_cam.archivos`. La clave es determinista por
petición para que un reintento no cree otro objeto. Si B2 no confirma la subida,
no se crea disponibilidad en nube, la petición queda en error y el archivo SD
no se elimina. Las rutas `GET /api/v1/archivos/...` consultan únicamente
metadatos registrados; `/visualizacion` genera una URL prefirmada privada de
cinco minutos, que nunca se persiste en MongoDB.

## Sensor PIR por cámara

La integración PIR está destinada a Raspberry Pi 3 Model B+ con Raspberry Pi
OS y `python3-gpiozero`. El pin BCM es local a cada instalación (`PIR_PIN_BCM`)
y nunca se presupone. La salida OUT del módulo debe ser compatible con 3,3 V;
una señal de 5 V requiere adaptación antes de conectarse al GPIO. El Dashboard
persiste por cámara `pir_habilitado`, `pir_tipo_captura` y un cooldown validado
entre 3 y 3600 segundos. Al detectar movimiento, la Raspberry crea una petición
existente de origen `pir` y sigue el mismo flujo de SD, FastAPI y B2. El callback
GPIO se entrega al ciclo Qt para no bloquear la interfaz. Sin hardware o ante
un error del sensor, las peticiones manuales continúan funcionando.

## 1. Propósito de esta etapa

Esta etapa continúa el sistema existente sin reemplazar su arquitectura. El
objetivo fue conectar la aplicación de Raspberry Pi con FastAPI mediante HTTP
para que una petición creada en el Dashboard pueda ser ejecutada por la cámara.

La solución utiliza polling. La Raspberry consulta periódicamente a FastAPI si
hay una petición pendiente para su cámara. FastAPI es el único componente que
accede a MongoDB; la Raspberry no conoce ni utiliza la URI de la base de datos.

## 2. Arquitectura implementada

```text
Usuario
  |
  v
Dashboard PySide6
  |
  | POST /api/v1/peticiones
  v
FastAPI -------------------- MongoDB Ani_cam
  ^                              |
  | GET petición pendiente        | peticiones y archivos
  | PUT resultado                 v
Raspberry Pi con PySide6 y Picamera2
  |
  v
Foto JPEG o video MP4 en la tarjeta SD
```

El Dashboard no se comunica directamente con la Raspberry. El Dashboard crea y
consulta peticiones a través de FastAPI. La Raspberry también usa FastAPI, pero
solo para pedir su trabajo pendiente e informar su resultado.

## 4. Flujo de una petición de foto

1. El usuario selecciona `Camara 1` en la pestaña Peticiones del Dashboard.
2. El usuario presiona `Solicitar foto`.
3. El Dashboard envía `POST /api/v1/peticiones` a FastAPI con `camara_id` y
   `tipo: foto`.
4. FastAPI verifica que `camara001` existe en `Ani_cam.camaras`.
5. FastAPI crea el documento en `Ani_cam.peticiones` con estado `pendiente`.
6. La Raspberry configurada con `CAMARA_ID=camara001` consulta periódicamente
   el endpoint de pendientes.
7. FastAPI devuelve la petición pendiente más antigua de esa cámara.
8. La Raspberry usa `ControladorCamara.tomar_foto` para generar el JPEG local.
9. La Raspberry llama a FastAPI para informar el resultado y la ruta local.
10. FastAPI inserta los metadatos en `Ani_cam.archivos`, enlaza el archivo con
    la petición y cambia su estado a `ejecutado`.
11. Cuando el Dashboard actualiza la tabla, muestra `ejecutado` y el nombre del
    archivo. La Raspberry permite ver la imagen local en su propia interfaz.

Si la cámara no puede capturar la imagen, la Raspberry informa `error` y un
mensaje explicativo. FastAPI guarda ese mensaje en la petición.

## 5. Flujo de una petición de video

El inicio del flujo es igual al de foto. La diferencia es la ejecución local:

1. La Raspberry recibe una petición cuyo `tipo` es `video`.
2. `ControladorCamara.iniciar_video` inicia la grabación con Picamera2,
   `H264Encoder` y `FfmpegOutput`.
3. Después de la duración configurada, `ControladorCamara.detener_video`
   finaliza el MP4.
4. La Raspberry informa el resultado a FastAPI.
5. FastAPI registra el archivo y actualiza la petición a `ejecutado`.

La duración por defecto es diez segundos. Se puede cambiar sin editar código
definiendo la variable de entorno `DURACION_VIDEO_SEGUNDOS`.

## 6. Colecciones y relaciones de MongoDB

La base utilizada continúa siendo exclusivamente `Ani_cam`.

### camaras

La cámara utiliza un identificador textual, por ejemplo:

```json
{
  "_id": "camara001",
  "nombre": "Camara 1",
  "ubicacion": "Sector Norte",
  "estado": "activa"
}
```

### peticiones

Una petición representa una orden explícita del usuario, no un evento de cámara.

```json
{
  "_id": "ObjectId generado por MongoDB",
  "camara_id": "camara001",
  "tipo": "foto",
  "estado": "pendiente",
  "fecha_hora": "2026-09-25 10:30:00"
}
```

Después de una ejecución correcta se agregan `archivo_id` y `nombre_archivo`.
Después de un fallo se agrega `mensaje_error`. Estos campos son opcionales para
mantener la compatibilidad con las peticiones creadas antes de esta integración.

### archivos

La colección ya existía. Se mantiene su campo histórico `id_camara`. Para una
captura solicitada se conserva esa relación y se agregan los datos mínimos para
conectarla con la petición:

```json
{
  "id_camara": "camara001",
  "peticion_id": "ObjectId de la petición convertido a texto",
  "tipo": "imagen",
  "nombre_archivo": "/ruta/local/de/la/Raspberry/foto_001.jpg",
  "ruta_local": "/ruta/local/de/la/Raspberry/foto_001.jpg",
  "fecha_hora": "2026-09-25 10:30:15"
}
```

Para video, `tipo` es `video`. No se completa `id_evento`, porque una petición
del Dashboard no debe convertirse artificialmente en un evento.

La relación completa queda así:

```text
camara._id -> peticiones.camara_id
peticiones._id -> archivos.peticion_id
peticiones.archivo_id -> archivos._id
```

## 7. Endpoints relacionados con peticiones

### POST /api/v1/peticiones

Lo consume el Dashboard. Crea una petición en estado `pendiente`.

```json
{
  "camara_id": "camara001",
  "tipo": "foto"
}
```

### GET /api/v1/peticiones

Lo consume el Dashboard para mostrar el historial actualizado de peticiones,
incluido el archivo generado o el mensaje de error cuando existen.

### GET /api/v1/peticiones/pendientes/{camara_id}

Lo consume la Raspberry. Devuelve solo la petición pendiente más antigua de la
cámara indicada; si no hay ninguna, responde `null`. Esta ruta no modifica la
base de datos.

Ejemplo:

```text
GET /api/v1/peticiones/pendientes/camara001
```

### PUT /api/v1/peticiones/{peticion_id}/resultado

Lo consume exclusivamente la Raspberry al finalizar una captura. Acepta solo
los estados finales `ejecutado` o `error`; no permite crear estados nuevos.

Ejemplo de captura correcta:

```json
{
  "estado": "ejecutado",
  "nombre_archivo": "foto_001.jpg",
  "ruta_local": "/home/pi/proyecto/archivos/camara001/fotos/foto_001.jpg"
}
```

Ejemplo de error:

```json
{
  "estado": "error",
  "mensaje_error": "No se pudo inicializar la camara."
}
```

Si una petición ya fue resuelta, FastAPI rechaza otro resultado con HTTP 409.
Esto protege el historial contra actualizaciones tardías o duplicadas.

## 8. Interfaz de la Raspberry

La nueva ventana de `raspberry_prueba` tiene el propósito de supervisar las
peticiones del Dashboard. Muestra el estado de conexión con FastAPI, el ID de
la cámara asociada, el historial recibido durante la sesión, su tipo, estado,
fecha y resultado.

No incluye botones para solicitar una captura manual. La orden nace siempre en
el Dashboard. Cuando una petición ejecutada tiene un archivo local disponible,
la interfaz puede mostrar una foto o reproducir un video.

Si FastAPI deja de responder, la aplicación no se cierra: muestra el estado de
desconexión y vuelve a intentarlo en el siguiente intervalo de consulta.

## 9. Configuración de la Raspberry

En Raspberry Pi OS se mantienen las dependencias de cámara instaladas con apt:

```bash
sudo apt update
sudo apt install -y python3-picamera2 ffmpeg python3-pyside6.qtwidgets python3-pyside6.qtmultimedia
```

También se requiere `requests`, declarado en `raspberry_prueba/requirements.txt`.

Antes de iniciar la aplicación se debe indicar la IP de la computadora que
ejecuta FastAPI. No debe utilizarse `127.0.0.1` para una Raspberry remota,
porque esa dirección apunta a la propia Raspberry.

```bash
export URL_BACKEND="http://192.168.1.50:8000/api/v1"
export CAMARA_ID="camara001"
export INTERVALO_CONSULTA_MS="5000"
export DURACION_VIDEO_SEGUNDOS="10"
python3 main.py
```

La IP `192.168.1.50` es solamente un ejemplo y debe reemplazarse por la IP real
de la PC del backend. FastAPI debe iniciarse escuchando una dirección accesible
desde la red local, no solo `127.0.0.1`.

## 11. Límites actuales

- Los archivos permanecen en la tarjeta SD de la Raspberry; no se suben a la
  nube ni se transfieren al Dashboard.
- La reproducción y visualización de archivos se realiza localmente en la
  Raspberry, no desde el Dashboard.
- No se implementaron MQTT, Redis, RabbitMQ, WebSockets, Docker ni servicios de
  mensajería, porque no son necesarios para esta etapa educativa.
- Los eventos continúan siendo un historial independiente y no se crean desde
  las peticiones.

## 14. Inicio en red y comprobaciones previas

El orden de inicio evita errores confusos entre componentes dependientes:

1. Iniciar MongoDB y comprobar que responde. FastAPI ejecuta un `ping` a
   MongoDB durante su ciclo de vida; por ello necesita `Ani_cam` disponible
   antes de aceptar peticiones.
2. Desde la carpeta `backend`, iniciar FastAPI exactamente con:

```bash
uvicorn main:app --host 0.0.0.0 --port 8000 --reload
```

`uvicorn` es el servidor ASGI; `main:app` selecciona la instancia FastAPI del
archivo `main.py`; `--host 0.0.0.0` abre escucha en las interfaces de red de la
PC; `--port 8000` define el puerto TCP; y `--reload` sirve para desarrollo.
El comando reducido `uvicorn main:app --reload` puede dejar el proceso accesible
solo desde la PC. `GET /health` confirma el backend y MongoDB sin modificar
colecciones.
3. Obtener la IPv4 de la PC con `ipconfig` y probar desde la Raspberry:

```bash
ping IP_DE_LA_PC
```

Una respuesta prueba conectividad IP básica. Si no la hay, revisar dirección,
conexión de ambos equipos, firewall, puerto y la escucha de FastAPI. En una red
local normalmente están en la misma red, por Wi-Fi o Ethernet, aunque el requisito
real es que exista una ruta de red entre ambos.
4. Configurar en la Raspberry `URL_BACKEND`, por variable de entorno o en
`config.py`, con la URL **base de la API**:

```python
URL_BACKEND = "http://192.168.1.100:8000/api/v1"
```

La IP es solo un ejemplo y debe reemplazarse. `localhost` y `127.0.0.1` siempre
identifican el propio equipo: en la Raspberry no identifican la PC que ejecuta
FastAPI. El sufijo `/api/v1` es necesario porque `ClienteBackend` agrega las
rutas de peticiones a esa URL base.
5. Iniciar la aplicación de Raspberry y, por último, el Dashboard. De este modo
el Dashboard solo crea peticiones cuando el backend está disponible, y la
Raspberry puede recogerlas desde su siguiente intervalo de polling.

## 15. Reproducción MP4: hallazgo y límite de validación

La interfaz reproduce con `QMediaPlayer` y `QVideoWidget` de PySide6/Qt
Multimedia. El código de captura usa `H264Encoder` de Picamera2 y
`FfmpegOutput`, por lo que el video se genera como flujo H.264 encapsulado en
MP4. La versión instalada y declarada en la PC de desarrollo es PySide6 6.7.2;
en Raspberry Pi OS el backend efectivo depende de la distribución y sus paquetes
multimedia, por lo que debe comprobarse en la Raspberry real.

Un MP4 válido en otra computadora no demuestra que el backend de Qt de la
Raspberry disponga del mismo códec o complemento. Se agregó manejo de las señales
asíncronas `errorOccurred` y `mediaStatusChanged`: cuando Qt comunica un error,
ANICAM detiene esa reproducción, informa el detalle y conserva abierta la
ventana y el polling. No se reemplazó Qt Multimedia sin una reproducción física
del problema.

Para investigar una caída nativa aún no reproducida, guardar la salida de
consola y ejecutar en la Raspberry, sobre el mismo archivo:

```bash
ffprobe archivo.mp4
ffmpeg -v error -i archivo.mp4 -f null -
```

Después revisar `python3-pyside6.qtmultimedia`, `ffmpeg`, el escritorio gráfico
y la reproducción mediante un reproductor externo. Esto separa un MP4 defectuoso
de una incompatibilidad del backend Qt. Una terminación del proceso dentro de
una biblioteca nativa no puede atraparse desde Python, pero los errores que Qt
emite como señal ya no cierran ANICAM.

## 16. Auditoría de estructura y españolización

La revisión completa comprobó los módulos Python rastreados de `backend`,
`desktop_app` y `raspberry_prueba`, sus imports locales y sus archivos
`__init__.py`. No se encontraron directorios vacíos rastreados ni README raíz
duplicados. Se conservan `README.md` y `README.txt` como guías generales, y el
README de Raspberry porque documenta dependencias de hardware que no corresponde
duplicar por completo en la raíz.

Se eliminó `backend/app`: contenía únicamente un `__init__.py` con una promesa
de arquitectura futura. No era importado ni contenía código activo, por lo que
su eliminación no modifica FastAPI, endpoints ni la conexión con `Ani_cam`.

Los `__init__.py` restantes se mantienen como marcadores de paquetes y como
descripción breve de la responsabilidad de cada carpeta. Aunque Python moderno
puede trabajar con paquetes de espacio de nombres, conservarlos hace explícita
la estructura educativa y evita cambios innecesarios en imports existentes.

Los nombres que pertenecen a tecnologías externas se conservan por
compatibilidad: `FastAPI`, `APIRouter`, `QMainWindow`, `QMediaPlayer`,
`Picamera2`, `ObjectId`, `MongoClient`, `requests`, los métodos HTTP y las URLs
de la API. Los nombres propios nuevos o modificados se expresan en español,
como `servicio_proyecto.py`, `obtener_informacion_proyecto`,
`TAMANO_FOTO` y `TASA_BITS_VIDEO`.

La revisión específica de Raspberry cubrió `config.py`, `main.py`, cámara,
almacenamiento, comunicación, interfaz y pruebas. Cada módulo explica su
responsabilidad, composición, herencia cuando aplica, señales Qt, polling HTTP,
persistencia local y el límite entre Raspberry, FastAPI y MongoDB.
